# retryfetch – What's New

## Changes that may affect you

- **Default timeout is now 10 seconds (was 30).** Each attempt now gives up after 10 seconds unless you set `timeoutMs`. If you have slow endpoints, set `timeoutMs: 30000` to keep the old behavior.
- **Only temporary errors are retried.** Requests are now retried on `429` (Too Many Requests) and `5xx` server errors only. Other `4xx` responses, such as `400`, `401`, `403` and `404`, are returned right away instead of being retried. This avoids wasted attempts on requests that can't succeed.
- **Node.js 18 or newer is required.** Node 16 is no longer supported.

## New

- **Jitter option for backoff.** Set `jitter: true` to randomize each retry delay between 0 and the normal backoff value. This helps avoid many clients retrying at the same moment. It is off by default.
- **Circuit breaker (experimental).** `experimental.circuitBreaker()` is a standalone helper that stops sending requests after repeated failures and allows them again after a cool-down. It is not connected to `retrying` yet, and its shape may change, so don't rely on it in production.

## Fixed

- **Cleaner cancellation handling.** Abort listeners added through the `signal` option are now removed once a request finishes, which prevents listeners from building up when you reuse one signal across many requests.

## Docs

- The options reference now notes that `timeoutMs` is in milliseconds and documents `jitter`.

# retryfetch release notes

Read this to learn what changed since 2.3.0 and what you need to do before you upgrade. It is for developers who use retryfetch in their applications.

**Version:** [Version to be set before release]
**Date:** [Release date to be set]

## Overview

This release changes three default behaviors. Check them before you upgrade, because they can change how your application behaves without any code change on your side.

- **Shorter timeout:** Each attempt now times out after 10 seconds instead of 30 seconds.
- **Fewer retries:** retryfetch now retries only on status 429 and 5xx. It no longer retries other 4xx statuses.
- **Node 18 or later:** Node 16 is no longer supported.

This release also adds a `jitter` option and fixes a memory leak. It also adds an experimental circuit breaker. Read "Before you upgrade" first, then the sections for the features you use.

## Before you upgrade

Check each item in this list.

1. **Check your timeout.** If you do not set `timeoutMs`, requests now fail with a `TimeoutError` after 10 seconds. To keep the old limit, set `timeoutMs: 30000`.
2. **Check your retry needs.** retryfetch no longer retries a response such as 400, 404 or 408. If you relied on those retries, retry in your own code.
3. **Check your Node version.** Run `node --version`. Use version 18 or later. We tested on Node 18, 20 and 22.

## Changes that affect existing code

### Requests time out after 10 seconds by default

The default `timeoutMs` is now `10000` (10 seconds). It was `30000` (30 seconds). The timeout applies to each attempt, not to the whole call.

To keep the old behavior, pass the option:

```js
retrying(fetch, { timeoutMs: 30000 });
```

### Only 429 and 5xx responses trigger a retry

retryfetch now retries when the response status is 429 or 500 and above. Before, it retried on every status of 400 and above. Other client errors, such as 400, 401, 403 and 404, now return at once. Retrying them rarely helps, and it delayed your error handling.

### Node 16 is no longer supported

retryfetch now requires Node 18 or later.

## New features

### Spread out retries with the jitter option

Set `jitter: true` to randomize each wait before a retry. The wait becomes a random value between 0 and the normal backoff delay. This stops many clients from retrying at the same moment. The default is `false`, so existing behavior does not change.

```js
retrying(fetch, { jitter: true });
```

### Try the experimental circuit breaker

`experimental.circuitBreaker()` stops requests for a while after repeated failures. Use it at your own risk:

- **Experimental:** Its API may change in any release, including a minor one.
- **Standalone:** `retrying` does not use it. You call it yourself around your requests.

It takes three options. All are optional:

| Option | Default | Meaning |
|--------|---------|---------|
| `failureThreshold` | 5 | Failures in a row before requests stop |
| `resetMs` | 30000 | Milliseconds to wait before requests are allowed again |
| `now` | `Date.now` | Clock function, mainly for tests |

The returned object has two methods. `canRequest()` returns `true` when you may send a request. `record(ok)` tells the breaker whether the last request succeeded.

```js
const { experimental } = require('retryfetch');
const breaker = experimental.circuitBreaker({ failureThreshold: 5, resetMs: 30000 });

if (breaker.canRequest()) {
  // send the request, then:
  breaker.record(true); // or false after a failure
}
```

## Fixes

### Abort listeners are now released

When you pass a `signal`, retryfetch used to keep a listener on it after each request finished. If you reused one signal for many requests, these listeners built up. retryfetch now removes the listener as soon as the request succeeds, fails or times out. You do not need to change anything.

# retryfetch release notes

Changes since version 2.3.0.

## Changes that may affect your app

**The default timeout is now 10 seconds (was 30 seconds).**
If a request takes longer than 10 seconds, it now fails with a timeout error. To keep the old behavior, set it yourself:

    retrying(fetch, { timeoutMs: 30000 })

**Fewer failed responses are retried.**
retryfetch now retries only on status 429 (too many requests) and 5xx (server errors). Other 4xx responses, such as 400, 401, 403, and 404, are returned right away instead of being retried. These errors normally mean the request itself is wrong, so retrying did not help and only added delay.

## New

- **Jitter option.** Set `jitter: true` to randomise each retry delay between 0 and the normal backoff time. This helps when many clients retry at once. It is off by default, so delays are unchanged unless you turn it on.
- **Experimental circuit breaker.** `experimental.circuitBreaker()` is a separate helper that stops sending requests after repeated failures. It is not connected to `retrying`. It is experimental and may change at any time, so we do not recommend using it in production yet.

## Fixed

- Fixed a small memory leak: when you pass a `signal`, retryfetch now removes its listener from the signal once the request finishes.

## Documentation

- The `timeoutMs` option is now documented as milliseconds.
- Added the `jitter` option to the options reference.
