# product-engineer v2 design

Date: 2026-09-05. Status: approved in conversation, implemented from this document.
Predecessor: `2026-09-05-product-engineer-skill-design.md` (the first release).

## Goal

Turn a single well-made skill into a repository people install, star, fork and extend:
the README shows the behaviour before it explains it, the skill becomes a pack of four
that each rank on skills.sh, every agent that reads instruction files gets the rules
without loading SKILL.md, and the measured claims stand on a harness that can be rerun
with repetition. The launch is Monday 7 September 2026; the pre-launch scope is what the
launch page shows first, the post-launch scope is what the first contributors will need.

## Sources

The product-engineer research report of 5 September 2026 (in the conversation record).
Facts and URLs in this document come from it; nothing here was invented for the launch.

## Pre-launch scope

### 1. README as a demo

Order of sections, top to bottom: wordmark and tagline, badges, one before/after commit
pair, one before/after final-message pair, a terminal demo of `check` failing then
passing, the install one-liner, Measured, the pack, the seven rules, Check and CI, What
it does not do, Where it comes from, Contributing, Stars. The install matrix ("Where it
lands"), the plugin commands and the by-hand copy move to `docs/install.md`; the README
links to it in one line.

The terminal demo is `assets/check-demo.svg`, a hand-written SVG of a real session
(`vhs` is not installed on the build machine). Its text is the literal output of
`node bin/check.mjs check` on two fixture messages kept under `test/fixtures/`, so the
picture can be regenerated by hand from a command anyone can run. If `vhs` becomes
available, `scripts/demo.tape` records the same session as a GIF.

### 2. Skill pack

Four skills, each a directory under `skills/` with its own `SKILL.md`, self-contained
so that installing one alone works:

| skill | what it carries | when it is the right install |
|---|---|---|
| `product-engineer` | the seven rules and the five reference files (unchanged content) | full behaviour for agents that write code |
| `customer-block` | rule 2 only: the block template and two before/after pairs, inline | teams that only want the commit and PR block |
| `done-means-observed` | rule 3 only: the observed checklist, inline, with the "could not check" form | teams that only want honest completion reports |
| `release-notes` | the stakeholder mode from the roadmap: rules for status updates and release notes written by an agent that does not touch code | product, support and founders' assistants |

Frontmatter on every SKILL.md follows the Agent Skills specification: `name` equal to
the directory name, `description` starting with "Use when", `license: MIT`, and
`metadata` with `author`, `version` and `source`. Each file stays under 120 lines.
`test/skill-structure.sh` checks all four (frontmatter fields, no em dashes, the
directory and name agree). `.claude-plugin/plugin.json` moves to version 0.3.0 and
`claude plugin validate .` must still pass; the marketplace entry keeps its category.

### 3. Adapters generated from SKILL.md

`scripts/generate-adapters.mjs` reads `skills/product-engineer/SKILL.md`, drops the
frontmatter, and writes the same rules into every instruction file the surveyed agents
read, each with a first line that says it is generated and where from:

| file | format detail |
|---|---|
| `.cursor/rules/product-engineer.mdc` | frontmatter `description`, `alwaysApply: true` |
| `.github/copilot-instructions.md` | plain Markdown |
| `GEMINI.md` and `gemini-extension.json` | the extension manifest names `GEMINI.md` as its context file and points at `skills/` |
| `.clinerules/product-engineer.md` | plain Markdown |
| `.kiro/steering/product-engineer.md` | frontmatter `inclusion: always` |
| `.windsurf/rules/product-engineer.md` | frontmatter `trigger: always_on` |
| `AGENTS.md` | a short preface for agents working in this repository, then the rules |

`node scripts/generate-adapters.mjs --check` exits 1 when any file differs from what it
would generate; CI runs it, so the adapters cannot drift from the skill.
`test/adapters.test.mjs` generates into a temporary directory and asserts the files,
their first lines and the seven rule headings.

### 4. Eval scoring artefacts

Two heuristics in `evals/score.mjs` are known to misfire and are fixed before the
existing transcripts are rescored (no API spend):

- `numbersWithMethod` removes fenced code blocks and inline code spans before splitting
  into sentences, and ignores sentences whose only digits are versions, issue numbers,
  years, hashes or identifiers.
- `scopeRespected` treats Markdown files as documentation rather than scope creep; a
  separate informational count "documented the change in a file not listed" is printed
  in the per-task table.

`evals/RESULTS.md` and the README table are regenerated from the rescoring and say so.

## Post-launch scope (same week)

### 5. `check` as integrations

- `integrations/commitlint/index.mjs`: a commitlint plugin exposing the rule
  `customer-block` (present, with `What changed:`), plus `integrations/commitlint/config.mjs`,
  a shareable config that enables it. Tested with the plugin's own function signature
  (`(parsed, when) => [passed, message]`) against fixture messages; no commitlint install
  needed.
- `.pre-commit-hooks.yaml` at the repository root with id `product-engineer-check`,
  `language: script`, `stages: [commit-msg]`, entry `scripts/pre-commit-check.sh`.
- `docs/install.md` gains the lefthook and husky snippets.
- `package.json` is publish-ready (`files`, `bin`, `prepublishOnly`), `npx publint`
  passes, and the package is not published: that needs the npm trusted publisher.

### 6. Eval v2 harness

- `evals/run.sh` takes `PE_EVAL_RUNS` (default 1). With more than one run, results land
  in `results/<task>/<condition>/run-<n>/`; the old flat layout is read as run 1.
- `evals/score.mjs` reports, per metric, the pass rate per arm, the paired per-task
  delta, and a bootstrap 95% confidence interval on the mean paired delta (10,000
  resamples, seeded, no dependencies). With one run per arm it prints the interval as
  unavailable rather than a fake one.
- `evals/judge.mjs`: a pairwise judge that asks `claude -p` which of two commit messages
  is truer to a diff and more useful to a non-engineer, with the rubric inline and the
  order randomised per pair. It is written and tested against a fake transcript; it is
  not run until Efe approves the spend.
- `evals/BENCHMARK.md`: the design for a fifty-diff subset of CommitSuite (what and why
  labels, permissive licences), the sampling rule, the labelling protocol with two
  raters and Cohen's kappa, and the cost estimate. Design only.

### 7. Reference files with attribution

New files under `skills/product-engineer/references/`, each ending with a "Where this
comes from" line naming the source URL. Text is paraphrased, never copied:

- `press-release.md`: rule 1 in the shape of a one-paragraph press release, after Amazon's
  working-backwards practice.
- `ship-show-ask.md`: which changes need the full block, which need one line, which need
  a conversation, after Rouan Wilsenach's article.
- `appetite.md`: the appetite line for rule 7, after Shape Up.
- `definition-of-done.md` gains one closing line, "what I would do differently", after
  the Toyota hansei habit, and rule 3 in SKILL.md names "go and see" as its lineage.

### 8. Plain-language tables per language

`plain-language.tr.md`, `plain-language.ja.md` and `plain-language.zh.md` carry the same
fifteen terms with plain sentences in that language, written for this repository. Each
file names the public plain-language guideline for that language as its style reference
(gov.uk style guide under OGL v3, plainlanguage.gov in the public domain, the EU clear
writing guide with its source line, Japan's Immigration Services Agency guideline on easy
Japanese); none of their text is reproduced.

### 9. Readability in `check`

`bin/readability.mjs` computes Flesch reading ease (English), LIX (any language) and
Ateşman (Turkish) from sentence, word and syllable counts. `check` prints one `info`
line for the customer block: LIX always, Flesch when `--lang en` (the default), Ateşman
when `--lang tr`. Never an error, never a warning; a number the author can watch.

### 10. Chinese README and the contribution rule

`README.zh-CN.md` mirrors `README.tr.md` in length. `CONTRIBUTING.md` states the rule:
a new rule or a change to one ships with an eval task under `evals/tasks/` and a
before/after pair in `references/`; a reference-only change needs the pair.

## Non-goals

An install counter or telemetry (skills.sh counts installs), an orchestrator, an LLM
inside the hook or the `check` CLI, a benchmark on millions of commits, publishing to
npm from this work, cross-listing pull requests on other repositories.

## Testing

`npm test` runs the structure script (all four skills), the hook test, `check` tests,
adapter tests, readability tests, commitlint plugin tests and the scorer tests. CI runs
the same on Ubuntu and macOS plus the adapter freshness check. Every prose file passes
`ai-slop-linter` at its default threshold.

## Risks

The pack splits attention across four skills; the README makes `product-engineer` the
default and names the other three as subsets. Generated adapter files add eight paths to
the repository root; each says it is generated. Rescoring changes the published numbers;
the README says the heuristics changed and links the diff.
